# ADR 0009: React workbench with a generated API client

## Context and Problem Statement

Clerks need one screen flow to price, book and label parcels, and the demo needs explicit loading, empty, expired
and failed states. The frontend must not drift from the API contract, and it must not become a second source of
business rules. How is the web app built and checked?

## Decision Drivers

- Type-level agreement with `contracts/shipping.openapi.yaml`.
- Few runtime dependencies to review.
- Accessibility as a requirement, with automated checks as a supplement to manual ones.

## Considered Options

1. React SPA on Vite with types generated by openapi-typescript and calls through openapi-fetch.
2. Server-rendered pages from the Java API.
3. React SPA with a hand-written fetch layer.

## Decision Outcome

Chosen option 1.

- Versions: React 19.3.0, TypeScript 7.0.2, Vite 8.3.6, Node 26.13.0, npm 11.20.0. Tests: Vitest 5.1.0, Testing
  Library 16.3.3, Playwright 1.65.0, axe-core 4.14.0.
- `packages/shipping-client` holds `src/schema.d.ts` generated by openapi-typescript 7.13.0 (never edited by hand)
  and a small `createShippingClient` wrapper around openapi-fetch 0.17.0 that adds the bearer token and
  `Correlation-Id`. `apps/shipping-web` calls the API only through this package.
- The web app keeps business rules on the server. It may format, disable and explain (for example disable booking
  of an offer whose `expiresAt` has passed), but the server's answer decides.
- No router, state-management, data-fetching or component library in v0.1: five routes, a small router on the
  History API, and plain CSS with custom properties as design tokens. Adding any runtime library needs a review and
  an allowlist entry.
- The demo token is held in memory only, never in `localStorage`, `sessionStorage` or cookies.
- Static checks: import boundaries and cycles only, by `tools/web-imports/check-imports.mjs` (Node standard library):
  feature folders do not import each other's internals; only `src/api/` imports the client package
  `@shipping-reference-platform/client`; no import cycles. dependency-cruiser and required frontend edges are deferred. The C4 relationship from the web app to the
  API is a network call that Java static checks cannot see; end-to-end tests verify it.
- The screen specification is `docs/ui/workbench.md`; its visual decisions are binding on implementation.

### Consequences

- Good, because a contract change that breaks the UI fails type checking before any test runs.
- Good, because the dependency set stays small enough to review.
- Bad, because a home-grown router and fetch hooks are code the project maintains.
- Bad, because the frontend has no required-edge check; an unused feature module is not reported.

### Confirmation

- `web`: `npm ci --ignore-scripts`; regenerate the client and fail on diff; type check; `check-imports.mjs` (with its
  own fixture tests under `node --test`); Vitest component tests (`ParcelForm.test.tsx`, `QuoteCardList.test.tsx`,
  `BookingForm.test.tsx`, `ShipmentDrawer.test.tsx`, `ProblemAlert.test.tsx`, `ThemeToggle.test.tsx`).
- `contract-e2e`: Playwright specs `quote-book-label.spec.ts`, `expired-quote.spec.ts`, `tenant-denial.spec.ts`,
  `prototype-flag.spec.ts`, `accessibility.spec.ts` (axe-core on every screen and state) against the API started
  with the `demo` profile.
