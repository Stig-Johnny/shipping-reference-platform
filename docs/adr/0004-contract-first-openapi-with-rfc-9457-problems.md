# ADR 0004: Contract-first OpenAPI 3.1.2 with RFC 9457 problem details

Amended on 2026-11-07: see [Amendment 2026-11-07](#amendment-2026-11-07-the-generated-client-is-deferred). The
sections before the amendment are the decision as accepted on 2026-11-06, unchanged.

## Context and Problem Statement

The web app and the API are built in parallel by different agents. Both need one agreed interface, and drift between
the Java controllers, the TypeScript types and the documentation must fail a build. Errors must be safe and
consistent so the UI can show labelled, specific messages. How is the HTTP interface defined and kept honest?

## Decision Drivers

- One file both sides build against before either side writes code.
- Few dependencies to review (ADR 0007).
- Errors that never leak stack traces, SQL or another tenant's data.

## Considered Options

1. Contract-first: hand-written Java controllers validated against the OpenAPI file; TypeScript types generated.
2. Code-first: generate the OpenAPI file from annotated controllers (for example springdoc).
3. Contract-first with Java server stubs generated by openapi-generator.

## Decision Outcome

Chosen option 1.

- `contracts/shipping.openapi.yaml`, OpenAPI 3.1.2 (JSON Schema 2020-12 dialect), is the authority. Version 3.1.2 is
  kept for tooling compatibility.
- Schemas are closed (`additionalProperties: false`), bounded (lengths, ranges, patterns, enums) and use no `null`.
  The server rejects unknown request members (`spring.jackson.deserialization.fail-on-unknown-properties=true`).
- Java controllers are written by hand. Tests validate each exercised response (status, headers, body) against the
  contract with a JSON Schema 2020-12 validator. The validator library is chosen and allowlisted in the Java
  bootstrap issue (candidate: `com.networknt:json-schema-validator`); it is a test-only dependency.
- `packages/shipping-client` contains types generated by openapi-typescript 7.13.0 and a thin wrapper around
  openapi-fetch 0.17.0. The web app calls the API only through it.
- Errors follow RFC 9457 as `application/problem+json`: stable `type` URIs under
  `https://shipping-reference-platform.example/problems/` (registry in the contract's description), fixed `title`
  per type, `status`, a safe `detail`, `instance` (request path) and a `correlationId` extension member. A resource
  of another tenant is reported exactly like a missing one. Framework errors (unparseable body, unknown path, wrong
  method or media type, unexpected exceptions) are mapped by the isolated `FallbackProblemHandler`; business
  outcomes are mapped by each module's web adapter from sealed results, not from exceptions.
- Every response carries `Correlation-Id`, generated by `CorrelationIdFilter` or reused from a valid request header,
  and logged in the MDC under `correlationId`.
- Contract changes are level 3. Breaking changes are not made in v0.1 without a version change of `info.version`
  and of the `/api/v1` prefix.

### Consequences

- Good, because the UI and API teams cannot disagree silently: generation or conformance tests fail.
- Good, because no server generator enters the dependency allowlist.
- Bad, because hand-written controllers can still accept inputs the contract forbids if a test does not exercise
  them; conformance is only as complete as the tests.
- Bad, because a closed schema makes every additive change a contract change that clients must regenerate for.

### Confirmation

- `java` runs `QuotesHttpContractTest`, `ShipmentsHttpContractTest` and `TenantsHttpContractTest` (each validates
  responses against the contract) and `ProblemDetailsHttpContractTest` (unknown path, wrong method, wrong media
  type, malformed JSON, unknown member, unexpected exception: correct type, no stack trace, correlation ID present).
- `web` regenerates `packages/shipping-client/src/schema.d.ts` and fails on any diff.
- `contract-e2e` runs the Playwright suite against the real API with the demo seed.
- Not enforced yet: a check that every documented operation and status code is exercised by at least one test, and
  OpenAPI style linting (docs/gaps.md).

## Amendment 2026-11-07: the generated client is deferred

- As in ADR 0009's amendment of the same date, the first runnable slice generates no TypeScript client:
  `packages/shipping-client`, openapi-typescript 7.13.0 and openapi-fetch 0.17.0 are deferred with the rest of the
  frontend tooling. The web app calls the API through one hand-written, typed adapter in
  `apps/shipping-web/src/api`, whose types are written by hand from the contract.
- The contract stays the authority, and the server's HTTP contract tests remain the contract gate:
  `QuotesHttpContractTest`, `ShipmentsHttpContractTest`, `TenantsHttpContractTest` and
  `ProblemDetailsHttpContractTest` validate every response they exercise against `contracts/shipping.openapi.yaml`.
- Consequence: the first consequence above, that the UI and API teams cannot disagree silently, holds only on the
  server's side for this slice. The web app's hand-written types can drift from the contract without failing a
  build; the end-to-end tests catch such drift only for the operations and fields they exercise (`docs/gaps.md`).
- Confirmation: the `web` check that regenerates `packages/shipping-client/src/schema.d.ts` is deferred; the other
  confirmations above are unchanged. Before this amendment, the planned enforcement also listed "web: client
  regeneration produces no diff".
